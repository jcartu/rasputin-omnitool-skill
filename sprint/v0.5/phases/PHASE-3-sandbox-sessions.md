# PHASE 3 — Persistent sandbox sessions

**Branch:** `sprint/v0.5-phase3`
**Estimated effort:** 4–6 hours
**Depends on:** Phase 2 approved

## Objective

Make sandbox state survive across multiple tool calls in the same goal (and optionally across goals). The current `tools/sandbox/index.py` provisions implicitly via HTTP and assumes the agent-infra/sandbox container is just there; every call is independent. After this phase, a goal's first sandbox call provisions or attaches to a session, and subsequent calls reuse it — files, installed deps, env vars, running processes survive.

## Why

The defining capability difference between a "code interpreter" and an "agent computer" is state across turns. A real agent installs `pandas` once, writes a CSV, then runs analysis — three separate tool calls, one shared filesystem. Today each call wipes state.

## Architecture

### Session model

```python
@dataclass
class SandboxSession:
    session_id: str           # ULID, generated by manager
    container_id: str         # the underlying sandbox container
    workspace_path: str       # path inside the sandbox (e.g. /workspace/sess-01H...)
    created_at: datetime
    last_used_at: datetime
    metadata: dict            # arbitrary, written by tools (e.g. installed packages)
```

Sessions live in `~/.rasputin/sessions/sandbox/<session_id>/`:
- `session.json` — the dataclass serialized
- `workspace/` — local mirror of the sandbox workspace (synced lazily or on demand)

### Lifecycle

1. **Provisioning.** First call with no `session_id` → manager assigns ULID, ensures a container exists (provisioning via the sandbox HTTP API or compose if available), creates a workspace dir inside.
2. **Attach.** Calls with a `session_id` → manager verifies the session is alive (container still running, workspace still present), refuses if dead.
3. **Reuse.** Tool reads the session's workspace_path and uses it as the working directory for `code_execute`, `file_upload`, etc.
4. **Eviction.**
   - **TTL:** sessions idle > `RASPUTIN_OMNITOOL_SANDBOX_SESSION_TTL_MIN` (default 60) are evicted.
   - **LRU:** if active session count > `RASPUTIN_OMNITOOL_SANDBOX_MAX_SESSIONS` (default 10), oldest non-active session is evicted.
   - **Explicit:** `agent/session_manager.py:evict(session_id)` callable.
5. **Persistence across goals.** A goal may pass `session_id` from a previous goal. Manager re-attaches if alive; raises `SESSION_EXPIRED` if not.

### How tools see this

`tools/sandbox/index.py` gets a new top-level input field `session_id` (optional). When present:
- For `code_execute`: the code runs in the session's workspace.
- For `file_upload` / `file_download`: paths are scoped to the session workspace.
- For `jupyter_kernels_list`: unchanged (operation is global to the sandbox host).

When `session_id` is absent:
- The tool auto-creates a session scoped to the current goal (use `goal_id` from the agent context).
- Returns the new `session_id` in the result so the model can pass it forward.

### Wiring into ReAct

Add a `session_id` field to the ReAct executor's tool-call result observation, surfaced to the model as part of the standard tool output schema. The system prompt for ReAct (see Phase 2) is updated to instruct the model to thread `session_id` through subsequent calls to the same tool.

class SandboxSessionManager:
    def __init__(self, root: Path, sandbox_url: str, ...): ...

Singleton-ish: `get_sandbox_session_manager()` returns a process-wide instance.

## The sandbox HTTP API contract

agent-infra/sandbox exposes (per its OpenAPI):

- `POST /v1/code/execute` — body `{code, language, timeout, cwd?}`
- `POST /v1/files` — upload, body has `destination`
- `GET /v1/files?path=...` — download
- `GET /v1/jupyter/kernelspecs` — list

There is no first-class "session" concept in the upstream sandbox. We implement sessions on top of:
- A dedicated workspace directory per session (`/workspace/sess-<id>`).
- Code execution with `cwd` set to that directory.
- Persistent processes via a per-session `tmux` or `nohup` (Phase 3 does NOT implement persistent processes — see "out of scope"; Phase 3 is filesystem state only).

If the upstream sandbox API has changed and these endpoints are different, halt and document. Do not invent endpoints.

## Acceptance criteria

- `pytest -v tests/test_sandbox_sessions.py` passes (10+ test cases).
- Two sandbox calls in the same goal share a workspace: the first call writes `/workspace/sess-X/foo.txt`; the second call's `code_execute` can read it.
- Explicit session passing works: a goal can pass `session_id` and reuse a workspace from a prior goal (if alive).
- TTL eviction works: a session unused for > TTL is evicted on next manager call.
- LRU eviction works: creating sessions beyond `max_sessions` evicts the oldest idle.
- A killed sandbox container produces a clean `SESSION_DEAD` error on next attach; the manager removes the session entry.
- ReAct executor surfaces the `session_id` from the first sandbox call into the model's observation; subsequent sandbox calls in the same goal reuse it (verified in trace).

## Unit-test scenarios that MUST exist

1. `create()` produces a unique ULID and writes `session.json`.
2. `attach()` succeeds for a live session, fails for an unknown ID.
3. `attach()` fails with `SESSION_DEAD` when the container has been removed.
4. Two `code_execute` calls in the same session share filesystem state.
5. Filesystem isolation across sessions: session A cannot see session B's files via the workspace path.
6. TTL eviction: create, advance clock past TTL, `garbage_collect()` evicts.
7. LRU eviction: create N+1 sessions when cap is N; oldest goes.
8. Explicit `evict()` removes the session entry and the local mirror dir.
9. `list(alive_only=True)` excludes evicted entries; `alive_only=False` shows tombstones for evicted-this-process sessions.
10. ReAct integration: a fake LLM that issues two sandbox calls; second call inherits `session_id` from first; both observations show consistent state.

## Self-verification

```bash
# Bring sandbox up
docker compose --profile cpu up -d sandbox
curl -sf http://localhost:8080/v1/health || { echo "sandbox not up"; exit 1; }

pytest -v tests/test_sandbox_sessions.py 2>&1 | tee sprint/v0.5/phase-3-pytest.log

# Live two-call demo
python -c "
from agent.session_manager import get_sandbox_session_manager
from tools.sandbox.index import run as sandbox_run

mgr = get_sandbox_session_manager()
sess = mgr.create()
print('session:', sess.session_id)

r1 = sandbox_run({'operation': 'code_execute', 'code': 'open(\"foo.txt\", \"w\").write(\"hi\")', 'language': 'python', 'session_id': sess.session_id})
print('write:', r1)

r2 = sandbox_run({'operation': 'code_execute', 'code': 'print(open(\"foo.txt\").read())', 'language': 'python', 'session_id': sess.session_id})
print('read:', r2)
assert 'hi' in r2.get('result', {}).get('stdout', ''), 'session state did not survive'
print('OK — session state survives across calls')
" 2>&1 | tee sprint/v0.5/phase-3-live-demo.log
```

## Halt conditions specific to Phase 3

- If the upstream sandbox API does not support `cwd` in `code_execute`, we cannot scope sessions by working directory. In that case, halt and propose either (a) running each session in a separate container OR (b) using filesystem prefixes inside one container with cooperative tools. Joshua needs to weigh in.
- If session_id cannot be plumbed through the existing tool callable signature without breaking the executor's calling convention, document the conflict and propose a typed `ToolContext` parameter instead of an `inputs` dict field.

## Out of scope for Phase 3

- Persistent processes inside a session (long-running daemons, web servers). Filesystem state only.
- Browser session state (Phase 4).
- Container-level resource caps (CPU pinning, memory limits). Use the upstream sandbox defaults.
- Per-session credential isolation (planned for a future sprint).
- Cross-machine session migration.
